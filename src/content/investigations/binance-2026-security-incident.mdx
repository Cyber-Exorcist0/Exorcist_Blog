## Executive Summary

On October 29, 2026, at approximately 20:05 UTC, Binance experienced the most financially significant security incident in the history of digital asset custody. Over an intensive twenty-minute window, attackers initiated unauthorized withdrawals across ten distinct blockchains, generating an aggregate gross asset movement of approximately $6.34 billion (with blockchain analytics firm TRM Labs estimating the outflow at $6.36 billion). The impacted networks included Ethereum, Bitcoin, Tron, the XRP Ledger, Solana, Avalanche, Polygon, Arbitrum, Optimism, and Base.

Initial public commentary mischaracterized the event as either an unheralded cryptographic compromise of private keys or an inherent protocol failure within Ethereum's account abstraction standards. Forensic disclosures from Binance, blockchain intelligence from TRM Labs and Chainalysis, and official advisories from the Federal Bureau of Investigation (FBI) established a far more intricate reality:

1. **Root Cause:** The underlying private keys governing Binance's custodial wallets were neither extracted nor mathematically compromised. Binance's Multi-Party Computation (MPC) signing clusters and Hardware Security Modules (HSMs) functioned as designed, but they signed malicious payloads because the attacker successfully compromised the trusted internal orchestration environment authorized to submit transaction requests to the signing pipeline.
2. **Multi-Stage Intrusions:** The intrusion was not an abrupt single-day breach. It was the culmination of a disciplined, four-month cyber campaign attributed by the FBI to the Democratic People's Republic of Korea (DPRK) state-sponsored hacking unit tracked as TraderTraitor (part of the Lazarus Group). The campaign combined a trojanized package manager package in June 2026, an elaborate social-engineering recruitment operation in September 2026, lateral pivoting through an internal AI-assisted developer utility on October 20, 2026, and the harvesting of a container deployment permission token.
3. **Execution Vector:** On October 29, 2026, the attacker logged into a compromised engineer workstation, deployed an unauthorized container into Binance's internal infrastructure using the harvested token, and executed scripts that queried the internal wallet-signing service directly.
4. **Ethereum Exploitation via EIP-7702:** On the Ethereum network, the attacker weaponized Ethereum Improvement Proposal 7702 (EIP-7702), a standard introduced during the Pectra hard fork to grant smart contract capabilities to Externally Owned Accounts (EOAs). By submitting 50 pre-signed authorization tuples to accommodate the rapidly incrementing nonces of high-frequency exchange hot wallet Binance 14, the attacker temporarily delegated the wallet's execution code to a malicious "sweeper" contract. The hot wallet was converted into an automated asset siphon, draining native Ether and ERC-20 tokens while evading traditional transaction monitoring systems.
5. **Mitigation and Resolution:** Binance terminated the Ethereum delegation at 00:10 UTC on October 30, 2026, by broadcasting a new authorization designating the null address. Rapid coordination between Binance, stablecoin issuers (Tether, Circle), and protocol security councils froze approximately $2.85 billion on-chain. Binance absorbed 100% of customer financial impact using its corporate balance sheet and Secure Asset Fund for Users (SAFU) reserves, replenishing 98% of affected token assets within 48 hours.

## Incident Overview

Centralized cryptocurrency exchanges operate under extreme infrastructural tension. To service hundreds of thousands of active traders, an exchange must maintain high-liquidity "hot wallets" connected to automated transaction-processing daemons. While the vast majority of customer assets reside in offline, multi-signature cold storage vaults, hot wallets must hold billions of dollars in liquid inventory to satisfy continuous withdrawal requests.

To protect these internet-facing balances without sacrificing real-time throughput, modern tier-one exchanges utilize distributed signing architectures, typically combining Multi-Party Computation (MPC) with Hardware Security Modules (HSMs). Under an MPC model, no individual server or human operator holds a complete private key. Instead, cryptographic key shares are distributed across isolated computing nodes. When an authorized withdrawal is approved by risk evaluation microservices, these nodes collaboratively construct a valid digital signature using threshold cryptography without ever reassembling the underlying private key in memory.

```text
+-----------------------------------------------------------------------------------+
|                        STANDARD EXCHANGE WITHDRAWAL FLOW                          |
+-----------------------------------------------------------------------------------+
| User Web / API Request                                                            |
|       |                                                                           |
|       v                                                                           |
| [Withdrawal Risk Engine] --(Evaluates Velocity, 2FA, IP, Device History)--> PASS  |
|       |                                                                           |
|       v                                                                           |
| [Internal Orchestration Service]                                                  |
|       |                                                                           |
|       v                                                                           |
| [Internal Wallet-Signing Service API]                                             |
|       |                                                                           |
|       +--> [MPC Node 1 (Key Share 1)]                                             |
|       +--> [MPC Node 2 (Key Share 2)] ===> Valid Mathematical Signature Produced  |
|       +--> [MPC Node 3 (Key Share 3)]                                             |
|       |                                                                           |
|       v                                                                           |
| [Blockchain Node Broadcast] ===> Valid On-Chain Transaction                       |
+-----------------------------------------------------------------------------------+
```

The October 29, 2026 breach demonstrated a critical architectural vulnerability in this workflow: the signing service acts as a cryptographic oracle. If an adversary bypasses the withdrawal risk engine and communicates directly with the internal wallet-signing service from an authenticated network location, the MPC cluster will faithfully generate valid signatures.

Between 20:05 and 20:25 UTC on October 29, 2026, the attackers executed an orchestrated barrage of unauthorized signing requests across ten blockchains:

* **Ethereum:** Siphoned over 167,464 native Ether (ETH) and massive quantities of ERC-20 tokens, notably Tether (USDT) and USD Coin (USDC), totaling approximately $3.79 billion.
* **Bitcoin:** Extracted approximately 18,270 BTC (valued at roughly $1.47 billion) through large-value consolidated UTXO transfers.
* **Tron:** Drained approximately $628 million in TRX and TRC-20 USDT.
* **XRP Ledger:** Siphoned approximately $296 million from active hot wallets.
* **Solana:** Extracted approximately $96 million in SOL and SPL tokens.
* **Secondary EVM Networks:** Drained approximately $70 million across Arbitrum, Base, Optimism, Polygon, and Avalanche.

The gross asset outflow reached approximately $6.34 billion, making it nominally the largest digital heist in history, surpassing earlier benchmark incidents such as the Ronin Network bridge exploit ($624 million in 2022) and the Bybit hot-wallet theft ($1.5 billion in February 2025).

<EditorialAlert type="analysis" title="GROSS IMPACT VS. PERMANENT LOSS">
Digital forensics analysts must differentiate between gross asset movement, frozen assets, and permanent financial loss. While $6.34 billion left Binance's wallets, roughly $2.85 billion in centralized stablecoins and token assets was successfully frozen on-chain within hours by token issuers and validator security councils. Furthermore, because Binance absorbed 100% of the financial impact using corporate treasury funds and its SAFU reserve, user balances suffered zero financial loss.
</EditorialAlert>

## Initial Access: The Developer Workstation

The origin of the intrusion dates to June 2026, when an engineer from Binance's Wallet DevOps team (designated **Engineer A** in official post-mortem filings) sought to install an AI-assisted command-line coding tool.

During the installation process, Engineer A searched public package repositories and search engines, inadvertently downloading and executing a trojanized **Homebrew** formula. The poisoned package masqueraded as a legitimate developer utility but contained a dual-stage post-exploitation loader.

```text
+-----------------------------------------------------------------------------------+
|                        JUNE 2026: SUPPLY-CHAIN FOOTHOLD                           |
+-----------------------------------------------------------------------------------+
| DevOps Engineer A Searches for AI Coding Tool                                     |
|       |                                                                           |
|       v                                                                           |
| Executes Poisoned Homebrew Formula / Package                                      |
|       |                                                                           |
|       +--> Stage 1: Legitimate Utility Compiled & Executed (Masks Attack)         |
|       +--> Stage 2: In-Memory Post-Exploitation Shell Script Spawned              |
|                   |                                                               |
|                   v                                                               |
|             Reconnaissance:                                                       |
|             - Scans Local Environment for AWS / K8s Configs                       |
|             - Reads ~/.zshrc, ~/.ssh, and Local Git Configurations                |
|             - Dumps Internal Corporate Directory & Team Responsibilities         |
|                   |                                                               |
|                   v                                                               |
|             Exfiltrates Identity Map to Attacker C2 Server                        |
+-----------------------------------------------------------------------------------+
```

Binance's endpoint security monitoring detected anomalous outbound beaconing from Engineer A's workstation shortly after the package executed. The incident response protocol was triggered:

* The infected laptop was disconnected from the network and impounded for forensic analysis.
* The device was decommissioned and replaced.
* Engineer A's Active Directory and Single Sign-On (SSO) credentials were fully rotated.
* Local API keys and SSH credentials discovered on the device were revoked.

Despite this rapid remediation, the initial compromise achieved its primary strategic objective: **reconnaissance**. During the window of execution, the malicious payload enumerated Engineer A's local git repositories, shell history, and corporate directory access. The threat actors mapped the organizational hierarchy of Binance's wallet engineering division, identifying specific colleagues, repository names, internal communication channels, and administrative responsibilities.

<EditorialAlert type="warning" title="FORENSIC BLIND SPOT: IDENTITY RECONNAISSANCE">
Rotating credentials and replacing hardware neutralizes active persistence, but it cannot revoke knowledge acquired by an attacker. The threat actors used the June 2026 incident to build a target list of engineers who possessed direct administrative privileges over Binance's custody orchestration pipelines.
</EditorialAlert>

## Social Engineering and Internal Compromise

Having mapped the wallet infrastructure team, the threat actors initiated a bespoke social-engineering operation in September 2026 targeting **Software Engineer B**, a developer with operational access to internal microservices.

The campaign aligned with established tradecraft documented by the Cybersecurity and Infrastructure Security Agency (CISA) in Alert AA22-108A regarding North Korean **TraderTraitor** operators. The attackers established contact on a prominent professional networking platform, posing as executive recruiters representing a well-funded decentralized finance startup.

```text
+-----------------------------------------------------------------------------------+
|                   SEPTEMBER 2026: RECRUITMENT SOCIAL ENGINEERING                  |
+-----------------------------------------------------------------------------------+
| Threat Actor Persona: "Project Director" at Fictitious DeFi Firm                  |

| Initial Approach on Professional Networking Platform (Referencing Engineer B's CV)|
|       |                                                                           |

|       |                                                                           |
|       v                                                                           |
| Stage 2 Technical Interview: Encrypted Chat App Session with Fake "CEO / CTO"     |
|       |                                                                           |
|       v                                                                           |
| Technical Assessment Delivery: Malicious Node.js / Python Coding Challenge        |
|       |                                                                           |
|       v                                                                           |
| Execution on Corporate Laptop: In-Memory Payload Injected; EDR Bypassed           |
+-----------------------------------------------------------------------------------+
```

The recruitment deception was executed with exceptional rigor:

1. **Persona Construction:** The attackers registered corporate domains, created interactive company websites, and maintained active corporate profiles across multiple platforms to substantiate the fictitious entity.
2. **Video Screening:** Engineer B attended a live video conference with a purported HR representative. The individual used deepfake visual filters or compromised identities to conduct a realistic behavioral screening.
3. **Technical Assessment:** For the second round, Engineer B was directed to an encrypted messaging platform to converse with a fake "Chief Technology Officer." The attacker provided a zip archive containing a technical coding challenge, requiring the candidate to debug an algorithm and run unit tests.
4. **Execution:** Engineer B cloned the repository and ran the test suite on a corporate-issued workstation. The project contained heavily obfuscated JavaScript/Python code that utilized an in-memory reflective loader.
5. **EDR Evasion:** The payload avoided dropping executable binaries to disk. Instead, it unpacked itself inside legitimate runtime processes (Node.js/Python), bypassing the endpoint detection and response (EDR) agent active on the machine.

The loader established an encrypted command-and-control (C2) channel disguised as standard HTTPS telemetry to a legitimate cloud service provider.

## Lateral Movement and Privilege Escalation

Once established on Engineer B's workstation, the attackers refrained from initiating noisy network port scans that would trigger internal Intrusion Detection Systems (IDS). Instead, on **October 20, 2026**, they leveraged an unexpected asset: **Binance's internal AI-assisted developer utility**.

Like many large-scale engineering organizations, Binance deployed an internal AI coding and productivity assistant. This tool was integrated with internal documentation repositories, Confluence spaces, codebases, and developer chat channels to assist engineers with code generation, infrastructure queries, and internal runbook searches.

By querying the internal AI assistant using Engineer B's authenticated credentials, the attackers effectively used the corporate LLM as an intelligence aggregator:

* The attackers submitted prompts asking for deployment instructions, cluster ingress controllers, and internal RPC endpoint documentation for the wallet infrastructure.
* The internal AI assistant, drawing from indexed internal confluence pages, code review snippets, and deployment logs, synthesized detailed architectural blueprints for the wallet services.
* Through these AI-provided paths, the attackers obtained administrative pivot vectors into systems associated with **Engineer A** (the DevOps engineer from the June incident) and **Engineer C** (a senior wallet software engineer).

Critically, upon inspecting Engineer A's workstation environment, the attackers uncovered an active **container deployment permission token**.

This token was an administrative credential used to deploy and manage containerized services within Binance's private Kubernetes orchestration cluster. The token was meant for automated deployment pipelines but had been cached in an accessible configuration profile without hardware-token binding or source-IP restrictions.

With this token in hand, the attackers possessed the authority to deploy arbitrary containers directly into Binance's internal production cloud environment.

## Compromising the Wallet Infrastructure

The primary safeguard protecting Binance's hot wallets was its Multi-Party Computation (MPC) signing infrastructure.

Under Binance's custody model:

* Private keys are never held in a single file or monolithic database.
* Mathematical key shares are distributed across independent signing nodes hosted in isolated network subnets.
* When a customer requests a withdrawal, the request passes through the user-facing web tier, traverses the **Withdrawal Risk Engine** (which evaluates velocity limits, two-factor authentication, device fingerprinting, and account history), and, if approved, is routed to the **Internal Wallet-Signing Service**.
* The signing service requests partial signatures from the distributed MPC nodes, aggregates them into a standard cryptographic signature, and broadcasts the transaction to the blockchain.

```text

|       |                                                              |            |

|       |                                              [Withdrawal Risk Engine]     |
|       v                                              (Blind to direct RPC calls)  |
| Direct RPC API Requests to Internal Wallet-Signing Service                        |
|       |                                                                           |
|       +--> "Sign Transaction [XRP, Amount: 296M, Destination: Attacker]"          |

```

The flaw was not cryptographic; it was **architectural**.

The MPC signing service verified whether incoming requests possessed valid network authentication and acceptable formatting. It was not designed to evaluate high-level business logic, velocity caps, or protocol-level delegation semantics. The signing service implicitly trusted requests originating from internal containers carrying verified production deployment credentials.

### The Execution Window

On **October 29, 2026**:

* **17:15 UTC:** The attackers accessed the workstation of Engineer C.
* **17:15 to 19:56 UTC:** Using Engineer A's container deployment token, the attackers provisioned a rogue, ephemeral container inside the production cluster. They uploaded custom automation scripts configured to query the internal signing service API.
* **20:05 UTC:** The automated scripts initiated signing commands.

The signing service received requests directly from the rogue container, evaluated the production credentials as valid, and commanded the MPC nodes to produce valid signatures. Because the requests bypassed the external withdrawal evaluation engine, no withdrawal velocity limits, customer balance checks, or 2FA checks were evaluated.

The attacker did not steal a private key. The attacker commandeered the **signing oracle**.

## Understanding the EIP-7702 Exploitation

On the Ethereum network, the attack diverged from conventional cryptocurrency thefts. Instead of dispatching hundreds of standard ERC-20 transfer transactions, the attackers weaponized **EIP-7702**, an Ethereum Improvement Proposal introduced in the **Pectra** hard fork.

### The Protocol Background: EIP-7702

EIP-7702 was designed by Ethereum core developers (including Vitalik Buterin) to bring Account Abstraction (smart account features) to standard Externally Owned Accounts (EOAs) without forcing users to migrate their assets to smart contract wallets (such as Safe or ERC-4337 smart contract accounts).

Under EIP-7702:

* A new Ethereum transaction type is introduced: **Transaction Type 0x04** (SET_CODE_TX_TYPE).
* A Type 0x04 transaction includes an **authorization_list**.
* Each authorization is a cryptographic tuple signed by an EOA owner:
  authorization = [chain_id, address, nonce, y_parity, r, s]
* When processed, the Ethereum Virtual Machine (EVM) sets the code of the authorizing EOA to a 23-byte delegation designator:
  0xef0100 ++ target_address
* For the duration of the delegation, whenever a transaction calls or sends funds to the EOA, the EVM executes the code located at target_address within the context of the EOA (preserving the EOA's balance, storage, and address).

```text
+-----------------------------------------------------------------------------------+
|                        EIP-7702 DELEGATION DESIGNATOR                             |
+-----------------------------------------------------------------------------------+
| Byte Position:   0x00     0x01     0x02    0x03 ... 0x16                          |
| Hex Data:       [ 0xef ] [ 0x01 ] [ 0x00 ] [ 20-Byte Smart Contract Address ]     |
| Purpose:        Magic Prefix (Delegation)  Implementation Target Contract         |
+-----------------------------------------------------------------------------------+
```

### The Attack: Why 50 Pre-Signed Authorizations Were Required

Binance operates high-frequency Ethereum hot wallets, most notably **Binance 14** (0x28C6c06298d514Db089934071355E5743bf21d60).

Because Binance 14 continuously processes outgoing customer withdrawals and sweeps deposits, its account **nonce** increments rapidly (often multiple times per second).

An EIP-7702 authorization tuple is strictly bound to a specific account nonce:

tuple.nonce == account.nonce

If the account nonce increments between the moment an authorization is signed and the moment the transaction is mined, the authorization is rejected by the EVM as invalid.

To overcome this moving-target obstacle:

1. Through the rogue container, the attackers commanded the internal signing service to generate **50 consecutive EIP-7702 authorizations** for Binance 14, spanning nonces N, N+1, N+2, through N+49.
2. The attackers bundled these 50 authorizations into a single Type 0x04 transaction.
3. Whichever nonce was active when the transaction was included in an Ethereum block, the corresponding authorization in the list was valid, instantly applying the delegation designator to Binance 14.

### The Malicious Sweeper Logic

The target address specified in the authorization was an attacker-deployed smart contract. The contract contained minimal, highly optimized bytecode designed to function as an automated sweeper:

```solidity
// Illustrative decompiled logic of the attacker's sweeper implementation
contract MaliciousDelegationSweeper {
    address payable private immutable attackerC2;

    constructor(address payable _c2) {
        attackerC2 = _c2;
    }

    // Fallback executed whenever Binance 14 receives a call
    fallback() external payable {
        _drainAssets();
    }

    receive() external payable {
        _drainAssets();
    }

    function sweepTokens(address[] calldata tokens) external {
        _drainAssets();
        for (uint256 i = 0; i < tokens.length; i++) {
            uint256 bal = IERC20(tokens[i]).balanceOf(address(this));
            if (bal > 0) {
                IERC20(tokens[i]).transfer(attackerC2, bal);
            }
        }
    }

    function _drainAssets() internal {
        uint256 ethBal = address(this).balance;
        if (ethBal > 0) {
            attackerC2.transfer(ethBal);
        }
    }
}
```

Because the EVM executed this code in the context of Binance 14 (address(this) was Binance 14), the contract had direct access to all native ETH and ERC-20 tokens held by the exchange wallet.

### Tactical Advantages of the Sweeper Vector

The weaponization of EIP-7702 conferred three operational advantages to the attackers:

1. **Evasion of Anomaly Detection:** External risk engines monitoring on-chain activity look for unauthorized transactions originating from unrecognized external addresses. In this incident, the transactions appeared as internal contract execution originating from Binance 14 itself.
2. **Continuous Deposit Sweeping:** The delegation remained active across subsequent blocks. When unsuspecting retail users or automated deposit engines sent new funds to Binance 14, the incoming transactions triggered the sweeper's execution logic, immediately routing the fresh deposits to the attacker's addresses.
3. **High-Density Extraction:** Rather than executing hundreds of discrete ERC-20 transfer transactions (each requiring independent signing and gas expenditure), a single call to sweepTokens() allowed the attacker to drain multiple asset balances in a single atomic transaction.

Over 167,464 ETH and billions in stablecoins were transferred out of Binance 14 before the delegation was neutralized.

### The Revocation Challenge and Execution

Neutralizing an EIP-7702 delegation is complex during an active security incident:

* Under EIP-7702, revoking a delegation requires the account owner to broadcast a new Type 0x04 authorization designating the **zero address** (0x0000000000000000000000000000000000000000).
* Upon receiving an authorization with target address(0), the EVM clears the delegation designator, resetting the account to standard EOA behavior.
* **The Gas Dilemma:** Because the sweeper contract continuously drained all native Ether from Binance 14, the wallet held zero ETH to pay gas fees for its own transactions.
* **The Solution:** EIP-7702 permits **sponsored transactions**. An external account (a relayer operated by Binance security) submitted the Type 0x04 transaction and paid the gas fees, carrying a valid authorization signed by Binance 14.

At **00:10 UTC on October 30, 2026** (08:10 Beijing Time), Binance successfully broadcast the revocation authorization, permanently clearing the sweeper bytecode from Binance 14 and halting further automated drainage.

### The Mechanics of On-Chain Asset Freezing

Within sixty minutes of the breach, Binance activated emergency incident response compacts with major stablecoin issuers and protocol consortiums:

1. **Centralized Smart Contract Freezing:** Tether Limited and Circle Internet Financial acted upon emergency requests supported by blockchain intelligence from TRM Labs. 3. **Legal Status of Frozen Assets:** Digital assets frozen via smart contract blacklists cannot be moved or transferred by the attacker. However, they are **not yet recovered**. ## Defensive Engineering and DFIR Lessons

The Binance 2026 security incident offers fundamental architectural lessons for digital asset custodians, exchange operators, and cloud infrastructure engineers:

### 1. Cryptographic Oracles Must Enforce Business Logic

Multi-Party Computation (MPC) and Hardware Security Modules (HSMs) provide robust mathematical protection against private key theft. However, an MPC system that blindly signs any authenticated request is fundamentally insecure.

* **Semantic Transaction Verification:** Signing services must not operate as simple cryptographic oracles. The signing cluster must possess independent verification engines that inspect the semantic payload of every transaction.
* **Protocol-Level Constraints:** Custodial signing services should enforce strict protocol whitelists. For institutional hot wallets, signing an EIP-7702 `SET_CODE_TX_TYPE` authorization must be prohibited by default or subjected to multi-signature human approval with mandatory timelocks.
* **Independent Rate Limiting:** Velocity limits and aggregate value caps must be enforced at the signing-cluster boundary, entirely independent of upstream microservices.

### 2. Hardening Internal AI Tooling

The use of an internal AI-assisted developer utility as a lateral pivot vector highlights an emerging threat surface:

* **Contextual Data Boundary Enforcement:** Internal AI models must not have unfettered read access to indexed Confluence repositories, deployment scripts, or secret stores.
* **Prompt Telemetry and Anomaly Detection:** Queries submitted to internal developer assistants should be monitored for automated reconnaissance patterns (such as mass queries regarding infrastructure topologies, signing keys, or CI/CD credentials).
* **Least-Privilege Context Retrieval:** AI coding assistants should only retrieve context from repositories explicitly assigned to the authenticated user's project group.

### 3. Decoupling Deployment Tokens from Production Workstations

The transition from a compromised developer endpoint to production infrastructure was facilitated by a cached container deployment token:

* **Short-Lived, Hardware-Bound Credentials:** Orchestration tokens (Kubernetes bearer tokens, cloud provider IAM credentials) must never exist as long-lived, static secrets on developer machines.
* **Zero-Trust Network Verification:** Even authenticated deployment tokens must be validated against device health posture, hardware security key presence, and source network boundaries.
* **Separation of Concerns:** Developers designing software must never hold deployment permissions over the production clusters hosting financial signing services.

## Outstanding Questions

While the operational and on-chain mechanisms of the October 29, 2026 incident are thoroughly documented, critical forensic questions remain under investigation:

1. **Specific Zero-Day Capabilities in the Recruitment Payload:** The precise vulnerability exploited by the obfuscated Node.js/Python test suite to achieve in-memory execution and evade modern EDR software has not been publicly detailed by Binance or security vendors.
2. **Internal AI Assistant Logging and Session Integrity:** Did the internal AI tool passively fulfill prompts submitted by the attacker, or did the threat actors actively poison the model's retrieval context? Detailed audit logs of the prompts and model responses generated on October 20 remain confidential.
3. **Legal Mechanics of Frozen Asset Recovery:** While approximately $2.85 billion in stablecoins and token assets remains immobilized on-chain, the legal framework for court-ordered asset forfeiture, smart contract burning, and re-issuance to Binance across multiple international jurisdictions remains complex and unresolved.
4. **On-Chain Laundering of Native Assets:** The threat actors retain control of over 18,270 BTC and over 160,000 ETH. Tracking the dispersal of these assets through privacy protocols, cross-chain mixers, and instant swap platforms remains an active, global law-enforcement operation.
