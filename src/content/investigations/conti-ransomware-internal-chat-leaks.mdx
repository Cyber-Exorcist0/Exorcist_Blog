## Executive Summary

In late February 2022, following an internal ideological split triggered by the Russian invasion of Ukraine, an anonymous entity operating under the Twitter handle `@ContiLeaks` (characterized in threat intelligence reporting as a Ukrainian security researcher or disaffected insider) began publishing internal communications, source code, and administrative documents belonging to the **Conti ransomware syndicate**.

The leaked data disclosed distinct communication archives—including tens of thousands of internal Jabber (XMPP) messages (frequently cited as over 60,000 in initial drops) and extensive message dumps from internal Rocket.Chat servers spanning 2020 through early 2022—alongside the C++ source code repositories for the **Conti v3 Windows locker payload** (`conti_v3.zip`).

The telemetry provided the global cybersecurity community with unprecedented visibility into cybercrime syndicate operations. Rather than operating as an informal collective of independent actors, Conti functioned through an organizational hierarchy resembling a software company—complete with human resources personnel, salaried core developers, system administrators, quality assurance testers, negotiators, and performance bonuses.

This technical investigation analyzes the organizational model revealed by the chat archives and examines the version-specific binary internals of the **Conti v3 Windows locker payload**, focusing on its use of the Windows Restart Manager API, multithreaded I/O Completion Ports (IOCP), and ChaCha20/RSA hybrid cryptography.

## The 2022 Conti Leaks: Chronology & Data Composition

In late February 2022, Conti leadership published an official statement on their leak site declaring allegiance to the Russian government and threatening retaliatory cyberattacks against critical infrastructure in nations opposing the invasion of Ukraine.

Following that announcement, an anonymous entity operating the `@ContiLeaks` account began publishing internal archives in sequential releases:

1. **Jabber & Rocket.Chat Communications:** Multiple archives containing tens of thousands of XMPP/Jabber chat logs (widely cited in cybersecurity reporting as over 60,000 messages in initial releases) and substantial communication databases from internal Rocket.Chat servers spanning from 2020 through early 2022.
2. **Operational Playbooks & Manuals:** Internal training materials documenting Cobalt Strike beaconing, Active Directory reconnaissance, privilege escalation, and lateral movement procedures.
3. **Source Code Repositories:** Leaks of compiled decryptor utilities, command-and-control (C2) tools, and the complete C++ Visual Studio source code for the **Conti v3 locker** (`conti_v3.zip`) in March 2022.

<EditorialAlert type="analysis" title="EVIDENTIARY BASIS: LEAK ARCHIVES AS INVESTIGATIVE DATA">
  The leaked chat logs provide valuable operational visibility into syndicate coordination, infrastructure, and payroll. However, digital forensic examiners must treat leaked internal communications with analytical caution: they reflect fragmented conversational contexts, alias rotations, translation nuances, and potential posturing among participants. They do not constitute an exhaustive record of all Conti operations, nor should every conversational assertion be treated as independently verified ground truth.
</EditorialAlert>

## Technical Deconstruction: The Conti v3 Windows Locker Payload

The technical analysis below specifically examines **Conti v3**, reflecting the leaked C++ MSVC solution and reverse-engineering findings documented in peer-reviewed academic research (*IEEE Access*, 2022).

### 1. Windows Restart Manager Abuse & Process Termination

Conti's rapid encryption throughput depended on overcoming file locking. In modern Windows enterprise environments, mission-critical applications—including Microsoft SQL Server (`sqlservr.exe`), Exchange Server, and virtual machine hypervisors (`vmware-vmx.exe`)—hold exclusive or shared file handles that block read/write operations by user-mode processes.

Earlier ransomware families addressed this by executing brute-force batch scripts (e.g., `net stop MSSQLSERVER` or `taskkill /f /im ...`). Conti v3 instead abuses the native Windows **Restart Manager API** (`RstrtMgr.dll`), an operating system facility originally designed to help installers and update engines identify applications locking specific files:

1. **`RmStartSession`:** Initializes a Restart Manager session and returns a unique session handle.
2. **`RmRegisterResources`:** Registers the target file path with the session.
3. **`RmGetList`:** Queries the operating system for an array of `RM_PROCESS_INFO` structures describing all processes and services holding active handles to the registered file.
4. **Targeted Process Termination:** The locker iterates through the returned list, opens each locking process via `OpenProcess(PROCESS_TERMINATE, ...)`, and terminates it using `TerminateProcess()`.

<TechnicalBreakdown
  title="Windows Restart Manager Process Unlocking Workflow"
  topic="WINDOWS INTERNALS & ENCRYPTION MECHANICS"
  complexity="Binary Internals"
>

```c
// ILLUSTRATIVE RECONSTRUCTION — NOT RECOVERED CONTI SOURCE CODE
// (Demonstrating the Windows Restart Manager API sequence used by Conti v3)
#include <windows.h>
#include <restartmanager.h>
#include <vector>

#pragma comment(lib, "rstrtmgr.lib")

BOOL TerminateLockingProcesses(LPCWSTR targetFilePath) {
    DWORD dwSessionHandle = 0;
    WCHAR szSessionKey[CCH_RM_SESSION_KEY + 1] = { 0 };

    // 1. Initialize Restart Manager session
    DWORD dwErr = RmStartSession(&dwSessionHandle, 0, szSessionKey);
    if (dwErr != ERROR_SUCCESS) {
        return FALSE;
    }

    LPCWSTR filesToRegister[] = { targetFilePath };
    BOOL bTerminatedAny = FALSE;

    // 2. Register target file resource to identify locking processes
    dwErr = RmRegisterResources(dwSessionHandle, 1, filesToRegister, 0, NULL, 0, NULL);
    if (dwErr == ERROR_SUCCESS) {
        UINT nProcInfoNeeded = 0;
        UINT nProcInfo = 0;
        DWORD dwRebootReasons = RmRebootReasonNone;

        // Query initial buffer size requirements
        dwErr = RmGetList(dwSessionHandle, &nProcInfoNeeded, &nProcInfo, NULL, &dwRebootReasons);
        if (dwErr == ERROR_MORE_DATA && nProcInfoNeeded > 0) {
            std::vector<RM_PROCESS_INFO> processInfoList(nProcInfoNeeded);
            nProcInfo = nProcInfoNeeded;

            // Retrieve list of applications holding open handles
            dwErr = RmGetList(dwSessionHandle, &nProcInfoNeeded, &nProcInfo, processInfoList.data(), &dwRebootReasons);
            if (dwErr == ERROR_SUCCESS && nProcInfo > 0) {
                for (UINT i = 0; i < nProcInfo; i++) {
                    // 3. Obtain process handle with termination rights
                    HANDLE hProc = OpenProcess(PROCESS_TERMINATE, FALSE, processInfoList[i].Process.dwProcessId);
                    if (hProc != NULL) {
                        if (TerminateProcess(hProc, 1)) {
                            bTerminatedAny = TRUE;
                        }
                        CloseHandle(hProc);
                    }
                }
            }
        }
    }

    // 4. Properly terminate the Restart Manager session
    RmEndSession(dwSessionHandle);
    return bTerminatedAny;
}
```

By terminating only the specific processes holding open handles rather than crashing system-wide services indiscriminately, Conti ensures the host remains operational while rendering databases and document stores accessible for encryption.

### 2. Multithreaded Concurrency via I/O Completion Ports (IOCP)

Sequential directory traversal and file encryption introduce severe I/O bottlenecks. Conti v3 addresses this by decoupling filesystem traversal from encryption using Windows **I/O Completion Ports (IOCP)**:

* **Processor-Scaled Worker Thread Pool:** Rather than hardcoding a static thread count across all machines, Conti v3 queries host hardware via `GetSystemInfo` to determine `dwNumberOfProcessors` (the number of logical processors). In the analyzed v3 codebase, it instantiates asynchronous worker threads scaled to this processor count (allocating up to `dwNumberOfProcessors * 2` worker threads depending on execution mode), maximizing multi-core throughput while avoiding CPU starvation.
* **Work Queue Distribution:** A master thread walks filesystem directories and network shares, packaging each qualifying file path into an IOCP work item dispatched via `PostQueuedCompletionStatus`.
* **Asynchronous Execution:** Dedicated worker threads waiting on `GetQueuedCompletionStatus` dequeue tasks, execute the Restart Manager check, perform file encryption, and append the metadata footer concurrently.

```text
┌─────────────────────────────────────────────────────────────┐
│ MASTER DIRECTORY TRAVERSAL THREAD                           │
│ - Enumerates volumes, local drives, and network shares      │
│ - Filters file extensions against exclusion lists           │
│ - Slices large target paths into asynchronous queue tasks   │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼ (PostQueuedCompletionStatus)
┌─────────────────────────────────────────────────────────────┐
│ WINDOWS I/O COMPLETION PORT (IOCP) WORK QUEUE               │
└──────┬───────────────────────┼───────────────────────┬──────┘
       │                       │                       │
       ▼                       ▼                       ▼
┌──────────────┐        ┌──────────────┐        ┌──────────────┐
│ WORKER T-01  │        │ WORKER T-02  │        │ WORKER T-NN  │
│ - RmGetList  │        │ - RmGetList  │        │ - RmGetList  │
│ - ChaCha20   │        │ - ChaCha20   │        │ - ChaCha20   │
│ - RSA Wrap   │        │ - RSA Wrap   │        │ - RSA Wrap   │
└──────────────┘        └──────────────┘        └──────────────┘
```

### 3. Cryptographic Pipeline: ChaCha20 / RSA Hybrid Encryption

Conti v3 employs a hybrid encryption scheme designed to balance high-speed throughput with robust asymmetric protection:

1. **Symmetric Encryption (ChaCha20):** For each target file, the worker thread generates a cryptographically random 256-bit symmetric key and 64-bit nonce. The file contents are encrypted using the ChaCha20 stream cipher. Academic analysis (IEEE Access, 2022) confirmed that Conti v3 implements configurable encryption modes (`-m` command-line flags): full encryption, partial 50% encryption (alternating blocks), and header-only encryption for large files and virtual machine disks (`.vmdk`, `.vhdx`) to maximize operational speed.
2. **Asymmetric Key Protection (RSA):** The per-file symmetric ChaCha20 key and nonce are encrypted using an embedded master public RSA key (typically RSA-4096 in standard enterprise builds, or RSA-2048 in select test/development builds).
3. **Metadata Footer:** The encrypted symmetric key, nonce, and marker metadata are appended to the end of the encrypted file. The original file extension is appended with the campaign extension.
4. **Historical Variant Distinction:** While CISA Advisory AA21-265A noted AES-256 and RSA-4096 in earlier Conti campaigns, the leaked Conti v3 source code analyzed in IEEE Access specifically implements ChaCha20 and RSA.
5. **Decryption & Recovery Design:** Under the intended cryptographic architecture, recovering the per-file ChaCha20 keys requires the syndicate's private RSA key. However, in practical incident response, victim recovery has at times been achieved through implementation bugs, memory extraction of active processes prior to reboot, unencrypted volume backups, or decryptors released following syndicate leaks.

### 4. Dynamic API Resolution & String Obfuscation

To hinder static analysis and reduce its Import Address Table (IAT) footprint, Conti v3 resolves critical Windows API functions dynamically at runtime:

* Rather than storing plaintext ASCII strings like `"VirtualAlloc"` or `"TerminateProcess"` in `.rdata`, Conti stores precomputed hash values using custom polynomial string-hashing algorithms.
* At initialization, the malware resolves module base addresses and walks the Export Address Table (EAT) of core system libraries (`kernel32.dll`, `ntdll.dll`, `rstrtmgr.dll`).
* It hashes each exported function name, compares it against the target precomputed hash, and obtains function pointers dynamically without exposing recognizable API strings to static inspection.

## Defensive Engineering & DFIR Lessons

The Conti syndicate's operational sophistication underscores several core defense-in-depth imperatives:

### 1. Disrupt the Early Kill Chain
Ransomware encryption is the final stage of an intrusion, not the first. By the time the Conti v3 locker binary executes, threat actors have typically spent days or weeks enumerating Active Directory, escalating privileges, and exfiltrating terabytes of data. Organizations must focus telemetry on early loader execution (BazarLoader, QakBot, TrickBot), Active Directory discovery queries (AdFind, BloodHound), and anomalous Cobalt Strike named-pipe traffic.

### 2. Behavioral Correlation of Restart Manager APIs
Calling Windows Restart Manager APIs (`RmStartSession`, `RmGetList`) is not inherently malicious; legitimate installers, updaters, and system maintenance utilities use these APIs routinely. Security products and EDR agents must therefore focus on **behavioral correlation**: unexpected user-mode processes (especially unsigned non-installer executables) initializing Restart Manager sessions, querying broad file paths across user directories, terminating critical services (such as `sqlservr.exe` or virtual machine hypervisors), and immediately initiating mass file modification.

### 3. Immutable and Isolated Backups
Because Conti operators routinely attempt to inhibit recovery by terminating database processes and deleting Volume Shadow Copies (via commands such as `vssadmin delete shadows`), organizations must maintain offline, immutable, or logically isolated backups protected by dedicated out-of-band credentials that cannot be modified via compromised Active Directory Domain Administrator accounts.
