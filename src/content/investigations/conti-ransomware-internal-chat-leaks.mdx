## Executive Summary

In late February 2022, following an internal ideological split triggered by the Russian invasion of Ukraine, an account operating under the name `@ContiLeaks` began publishing internal communications, source code, and administrative documents belonging to the **Conti ransomware syndicate**. Contemporary reporting described the source as allegedly Ukrainian, though the account operator's identity and precise motivations were not independently established.

The leaked data disclosed distinct communication archives—including tens of thousands of internal Jabber (XMPP) messages (widely cited in cybersecurity reporting as over 60,000 in initial drops, with subsequent releases expanding the total) and extensive message dumps from internal Rocket.Chat servers spanning 2020 through early 2022—alongside the C++ source code repositories for the **Conti v3 Windows locker payload** (`conti_v3.zip`).

The telemetry provided the global cybersecurity community with unprecedented visibility into cybercrime syndicate operations. Rather than operating as an informal collective of independent actors, Conti functioned through an organizational hierarchy resembling a software company—complete with human resources personnel, salaried core developers, system administrators, quality assurance testers, negotiators, and performance bonuses.

This technical investigation analyzes the organizational model revealed by the chat archives and examines the version-specific binary internals of the **Conti v3 Windows locker payload**, focusing on its use of the Windows Restart Manager API, multithreaded I/O Completion Ports (IOCP), and ChaCha20/RSA hybrid cryptography.

## The 2022 Conti Leaks: Chronology & Data Composition

On February 25, 2022, following the commencement of the Russian invasion of Ukraine, Conti leadership published an official statement on their leak site declaring allegiance to the Russian government and threatening retaliatory cyberattacks against critical infrastructure in nations opposing the invasion. While the group modified the statement hours later to adopt a slightly less aggressive tone, the political declaration triggered deep internal friction among participants and affiliates.

On February 27, 2022, an account operating under the name `@ContiLeaks` began publishing internal Conti information. Contemporary reporting described the source as allegedly Ukrainian, but the account operator's identity was not independently established. The leaks occurred in sequential tranches:

1. **Jabber & Rocket.Chat Communications:** Multiple archives containing tens of thousands of XMPP/Jabber chat logs (widely cited in cybersecurity reporting as over 60,000 messages in initial releases, with later releases expanding the corpus) and substantial communication databases from internal Rocket.Chat servers spanning from 2020 through early 2022.
2. **Operational Playbooks & Manuals:** Internal training materials documenting Cobalt Strike beaconing, Active Directory reconnaissance, privilege escalation, and lateral movement procedures.
3. **Source Code Repositories:** Leaks of compiled decryptor utilities, command-and-control (C2) tools, and in March 2022, the complete C++ Visual Studio source code for the **Conti v3 locker** (`conti_v3.zip`).

<EditorialAlert type="analysis" title="EVIDENTIARY BASIS: LEAK ARCHIVES AS INVESTIGATIVE DATA">
  The leaked chat logs provide valuable operational visibility into syndicate coordination, infrastructure, and payroll. However, digital forensic examiners and threat intelligence analysts emphasize the limitations of this dataset: it reflects fragmented conversational context, separate communication platforms (XMPP and Rocket.Chat), missing messages, unreadable OTR (Off-the-Record) encrypted sessions, alias rotations, translation nuances from Russian cybercrime slang, and potential posturing among participants. They do not constitute an exhaustive record of all Conti operations, nor should every conversational assertion be treated as independently verified ground truth.
</EditorialAlert>

## Technical Deconstruction: The Conti v3 Windows Locker Payload

The technical analysis below specifically examines **Conti v3**, reflecting the leaked C++ MSVC solution and reverse-engineering findings documented in peer-reviewed academic research (*IEEE Access*, 2022).

### 1. Windows Restart Manager API and Process Termination

Conti's rapid encryption throughput depended on overcoming file locking. In modern Windows enterprise environments, mission-critical applications—including Microsoft SQL Server (`sqlservr.exe`), Exchange Server, and virtual machine hypervisors (`vmware-vmx.exe`)—hold exclusive or shared file handles that block read/write operations by user-mode processes.

Earlier ransomware families addressed this by executing brute-force batch scripts (e.g., `net stop MSSQLSERVER` or `taskkill /f /im ...`). Conti v3 instead leverages the native Windows **Restart Manager API** (`RstrtMgr.dll`), an operating system facility originally designed to help installers and update engines identify applications locking specific files:

1. **`RmStartSession`:** Initializes a Restart Manager session and returns a unique session handle and session key.
2. **`RmRegisterResources`:** Registers target file paths with the session to identify which processes hold active locks.
3. **`RmGetList`:** Queries the operating system for an array of `RM_PROCESS_INFO` structures describing all processes and services holding active handles to the registered files. If the initial buffer size is insufficient, the API returns `ERROR_MORE_DATA` alongside the required element count (`nProcInfoNeeded`), allowing the locker to dynamically allocate the required memory buffer and repeat the query.
4. **Targeted Process Termination:** The locker iterates through the returned list, extracts each process identifier (`Process.dwProcessId`), opens the locking process via `OpenProcess(PROCESS_TERMINATE, ...)`, and terminates it using `TerminateProcess()`.
5. **`RmEndSession`:** Closes the Restart Manager session handle and releases associated operating system resources.

  title="Windows Restart Manager Process Unlocking Workflow"

```c
// ILLUSTRATIVE RECONSTRUCTION — NOT RECOVERED CONTI SOURCE CODE
// (Demonstrating the Windows Restart Manager API sequence and termination pattern)
#include <windows.h>
#include <restartmanager.h>
#include <vector>

#pragma comment(lib, "rstrtmgr.lib")

BOOL TerminateLockingProcesses(LPCWSTR targetFilePath) {
    DWORD dwSessionHandle = 0;
    WCHAR szSessionKey[CCH_RM_SESSION_KEY + 1] = { 0 };

    // 1. Initialize Restart Manager session
    DWORD dwErr = RmStartSession(&dwSessionHandle, 0, szSessionKey);
    if (dwErr != ERROR_SUCCESS) {
        return FALSE;
    }

    LPCWSTR filesToRegister[] = { targetFilePath };
    BOOL bTerminatedAny = FALSE;

    // 2. Register target file resource to identify locking processes
    dwErr = RmRegisterResources(dwSessionHandle, 1, filesToRegister, 0, NULL, 0, NULL);
    if (dwErr == ERROR_SUCCESS) {
        UINT nProcInfoNeeded = 0;
        UINT nProcInfo = 0;
        DWORD dwRebootReasons = RmRebootReasonNone;

        // Query initial buffer size requirements
        dwErr = RmGetList(dwSessionHandle, &nProcInfoNeeded, &nProcInfo, NULL, &dwRebootReasons);
        if (dwErr == ERROR_MORE_DATA && nProcInfoNeeded > 0) {
            std::vector<RM_PROCESS_INFO> processInfoList(nProcInfoNeeded);
            nProcInfo = nProcInfoNeeded;

            // Retrieve list of applications holding open handles
            dwErr = RmGetList(dwSessionHandle, &nProcInfoNeeded, &nProcInfo, processInfoList.data(), &dwRebootReasons);
            if (dwErr == ERROR_SUCCESS && nProcInfo > 0) {
                for (UINT i = 0; i < nProcInfo; i++) {
                    // 3. Obtain process handle with termination rights
                    HANDLE hProc = OpenProcess(PROCESS_TERMINATE, FALSE, processInfoList[i].Process.dwProcessId);
                    if (hProc != NULL) {
                        if (TerminateProcess(hProc, 1)) {
                            bTerminatedAny = TRUE;
                        }
                        CloseHandle(hProc);
                    }
                }
            }
        }
    }

    // 4. Properly terminate the Restart Manager session
    RmEndSession(dwSessionHandle);
    return bTerminatedAny;
}
```

Terminating processes that hold active file handles frees those files for immediate read/write access by subsequent encryption threads. However, terminating active database engines, hypervisors, and server daemons is inherently disruptive: it risks uncommitted transaction loss, application crash states, and severe operational interruption.

### 2. Multithreaded Concurrency via I/O Completion Ports (IOCP)

Sequential directory traversal and file encryption introduce severe I/O bottlenecks. In the leaked Conti v3 source code analyzed in *IEEE Access* (2022), the developers decoupled filesystem traversal from encryption using Windows **I/O Completion Ports (IOCP)**:

* **Processor-Scaled Worker Thread Pool:** Rather than hardcoding a static thread count across all machines, Conti v3 queries host hardware via `GetSystemInfo` to determine `dwNumberOfProcessors` (the number of logical processors). In the analyzed v3 codebase, it instantiates asynchronous worker threads scaled to this processor count (allocating worker threads proportional to `dwNumberOfProcessors`, typically up to `dwNumberOfProcessors * 2` depending on execution flags), maximizing multi-core throughput while avoiding CPU starvation.
* **Work Queue Distribution:** A directory traversal routine walks logical drives, mounted volumes, and accessible network shares, packaging discovered file paths into IOCP work items dispatched via `PostQueuedCompletionStatus`.
* **Asynchronous Execution:** Dedicated worker threads waiting on `GetQueuedCompletionStatus` dequeue tasks, execute the Restart Manager unlocking sequence if files are locked, perform file encryption, and append the metadata footer concurrently.

│ - Enumerates volumes, local drives, and network shares      │
│ - Filters file extensions against exclusion lists           │
│ - Slices target paths into asynchronous completion items    │
└──────────────────────────────┬──────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐

### 3. Cryptographic Pipeline: ChaCha20 / RSA Hybrid Encryption

Conti v3 employs a hybrid encryption scheme designed to balance high-speed throughput with robust asymmetric protection:

1. **Symmetric Encryption (ChaCha20):** For each target file, the worker thread generates a cryptographically random 256-bit symmetric key and 64-bit nonce. The file contents are encrypted using the ChaCha20 stream cipher. Academic analysis (*IEEE Access*, 2022) confirmed that Conti v3 implements configurable encryption modes (`-m` command-line flags): full encryption, partial 50% encryption (alternating blocks), and header-only encryption for large files and virtual machine disks (`.vmdk`, `.vhdx`) to maximize operational speed.
2. **Asymmetric Key Protection (RSA):** The per-file symmetric ChaCha20 key and nonce are encrypted using an embedded master public RSA key. The analyzed Conti v3 source code contains an embedded RSA-4096 public key in standard enterprise builds, alongside RSA-2048 keys observed in select development and test builds.
3. **Metadata Footer:** The encrypted symmetric key, nonce, and marker metadata are appended to the end of the encrypted file. The original file extension is appended with the campaign extension.
4. **Historical Variant Distinction:** While CISA Advisory AA21-265A documented AES-256 and RSA-4096 across earlier Conti campaigns, the leaked Conti v3 source code analyzed in *IEEE Access* specifically implements ChaCha20 and RSA. Similarly, while early campaigns appended the `.CONTI` extension, later campaigns and affiliate operations utilized randomized or victim-specific file extensions.
5. **Decryption Realities & Recovery:** Under strong hybrid encryption, reversing the ciphertext without the private RSA key is computationally infeasible. However, this does not mean recovery is universally impossible or that ransom payment is the only resolution. In practical incident response, victim recovery has been achieved through immutable offline backups, memory forensics capturing active keys prior to host reboot, implementation flaws in specific affiliate builds, or decryptors released publicly following syndicate leaks.

### 4. Dynamic API Resolution & String Obfuscation

To hinder static analysis and reduce its Import Address Table (IAT) footprint, Conti v3 resolves critical Windows API functions dynamically at runtime:

* Rather than storing plaintext ASCII strings like `"VirtualAlloc"`, `"TerminateProcess"`, or `"RmStartSession"` in `.rdata`, Conti stores precomputed hash values calculated using custom polynomial string-hashing algorithms.
* At runtime, the malware resolves module base addresses and walks the Export Address Table (EAT) of core system libraries (`kernel32.dll`, `ntdll.dll`, `rstrtmgr.dll`).
* It hashes each exported function name using the identical polynomial algorithm, compares the computed value against the target precomputed hash, and obtains function pointers dynamically without exposing recognizable API strings to static inspection.

## Defensive Engineering & DFIR Lessons

The Conti syndicate's operational sophistication underscores several core defense-in-depth imperatives:

### 1. Disrupt the Early Kill Chain
Ransomware encryption is the culmination of an intrusion, not the initial event. By the time the Conti v3 locker binary executes, threat actors have typically spent days or weeks enumerating Active Directory, escalating privileges, and exfiltrating sensitive data. Organizations must focus telemetry on early loader execution (BazarLoader, QakBot, TrickBot), Active Directory discovery queries (AdFind, BloodHound), and suspicious LSASS access.

### 2. Behavioral Correlation of Restart Manager APIs
Calling Windows Restart Manager APIs (`RmStartSession`, `RmRegisterResources`, `RmGetList`) is not inherently malicious; legitimate installers, updaters, and system maintenance utilities use these APIs routinely. Defensive monitoring must therefore avoid alerting solely on the presence of `RstrtMgr.dll`. Instead, security teams and EDR systems must focus on **behavioral correlation**: unexpected user-mode processes (especially unsigned non-installer executables) initializing Restart Manager sessions, querying broad file paths across user directories, terminating critical services (such as `sqlservr.exe` or hypervisors), and immediately initiating rapid file modification.

### 3. Immutable and Isolated Backups
Government advisories (CISA Alert AA21-265A) document Conti operators attempting to inhibit recovery by executing `vssadmin delete shadows` to purge Volume Shadow Copies. Because threat actors actively attempt to disable local recovery mechanisms, organizations must maintain immutable, logically isolated, or air-gapped backups protected by dedicated out-of-band credentials that cannot be compromised via Active Directory Domain Administrator accounts.
