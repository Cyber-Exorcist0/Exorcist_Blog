## Executive Summary

In late February 2022, following an internal ideological split triggered by the Russian invasion of Ukraine, an anonymous insider operating under the Twitter handle `@ContiLeaks` began publishing internal communications, source code, and administrative documents belonging to the **Conti ransomware syndicate**.

The leaked data disclosed tens of thousands of internal Jabber (XMPP) messages and hundreds of thousands of communications across Rocket.Chat and Jabber servers, alongside the C++ source code repositories for the **Conti v3 Windows locker payload** (`conti_v3.zip`). 

The telemetry provided the global cybersecurity community with an unprecedented autopsy of modern cybercrime syndicate operations. Conti did not operate as a loose confederation of hackers; it operated with the organizational hierarchy of a commercial software enterprise—complete with human resources personnel, salaried core developers, system administrators, quality assurance testers, negotiators, and performance bonuses.

This technical investigation dissects the organizational hierarchy revealed by the chat archives and examines the version-specific binary internals of the **Conti v3 Windows locker payload**, focusing on its use of the Windows Restart Manager API, multithreaded I/O Completion Ports (IOCP), and ChaCha20/RSA hybrid encryption.

## The 2022 Conti Leaks: Chronology & Data Composition

In February 2022, the Conti leadership published an official statement on their leak site declaring allegiance to the Russian government and threatening retaliatory cyberattacks against critical infrastructure in nations opposing the invasion of Ukraine. 

Almost immediately, an anonymous pro-Ukrainian researcher or disillusioned affiliate established the `@ContiLeaks` account and began disseminating internal archives in sequential tranches:

1. **Jabber & Rocket.Chat Communications:** Multiple archives containing tens of thousands of XMPP/Jabber chat logs (frequently cited as 60,000+ messages in initial dumps) and hundreds of thousands of messages across the syndicate's internal Rocket.Chat servers spanning from 2020 through early 2022.
2. **Operational Playbooks & Manuals:** Internal training guides for Cobalt Strike beaconing, Active Directory reconnaissance, privilege escalation, and network penetration.
3. **Source Code Repositories:** Leaks of compiled decryptor binaries, internal command-and-control (C2) utilities, and the complete C++ Visual Studio source code for the **Conti v3 locker** (`conti_v3.zip`).

<EditorialAlert type="analysis" title="EVIDENTIARY BASIS: LEAK ARCHIVES AS INVESTIGATIVE DATA">
  The leaked chat logs provide profound visibility into the syndicate's operational habits, payroll, and infrastructure. However, digital forensic examiners must acknowledge that the archives represent internal communications subject to operational security, alias rotation, and fragmented context. They do not constitute a complete record of every operation, nor should every statement made by operators in chat be treated as uncorroborated fact.

## Technical Deconstruction: The Conti v3 Windows Locker Payload

The technical analysis below specifically examines **Conti v3**, reflecting the leaked C++ MSVC solution and reverse-engineering findings documented in academic research (*IEEE Access*, 2022).

### 1. Windows Restart Manager Hooking & Process Termination

Conti's rapid encryption throughput depended on overcoming file locking. In modern Windows enterprise environments, mission-critical applications—including Microsoft SQL Server (`sqlservr.exe`), Exchange Server, and virtual machine hypervisors (`vmware-vmx.exe`)—hold exclusive or shared file handles that block read/write operations by user-mode processes.

Earlier ransomware families addressed this by executing brute-force batch scripts (e.g., `net stop MSSQLSERVER` or `taskkill /f /im ...`). Conti v3 instead uses the Windows **Restart Manager API** (`RstrtMgr.dll`), a native operating system facility designed to identify applications locking specific files during software updates:

1. **`RmStartSession`:** Initializes a Restart Manager session and returns a unique session handle.
2. **`RmRegisterResources`:** Registers the target file path with the session.
3. **`RmGetList`:** Queries the operating system for an array of `RM_PROCESS_INFO` structures describing all processes and services holding active handles to the registered file.
4. **Targeted Process Termination:** The locker iterates through the returned list, opens each locking process with `OpenProcess(PROCESS_TERMINATE, ...)`, and terminates it via `TerminateProcess()`.

  title="Windows Restart Manager Process Unlocking Workflow"

```c
// ILLUSTRATIVE RECONSTRUCTION — NOT RECOVERED CONTI SOURCE CODE
// (Demonstrating the Windows Restart Manager API sequence used by Conti v3)
DWORD TerminateLockingProcesses(LPCWSTR targetFilePath) {
    DWORD dwSessionHandle = 0;
    WCHAR szSessionKey[CCH_RM_SESSION_KEY + 1] = { 0 };

    // 1. Initialize Restart Manager session
    if (RmStartSession(&dwSessionHandle, 0, szSessionKey) != ERROR_SUCCESS) {
        return 0;
    }

    LPCWSTR filesToRegister[] = { targetFilePath };

    // 2. Register target file resource to identify locking processes
    if (RmRegisterResources(dwSessionHandle, 1, filesToRegister, 0, NULL, 0, NULL) == ERROR_SUCCESS) {
        UINT nProcInfoNeeded = 0;
        UINT nProcInfo = 16;
        RM_PROCESS_INFO processInfoList[16];
        DWORD dwRebootReasons = RmRebootReasonNone;

        // 3. Retrieve list of applications holding open handles
        if (RmGetList(dwSessionHandle, &nProcInfoNeeded, &nProcInfo, processInfoList, &dwRebootReasons) == ERROR_SUCCESS) {
            for (UINT i = 0; i < nProcInfo; i++) {
                // 4. Obtain handle with termination rights
                HANDLE hProc = OpenProcess(PROCESS_TERMINATE, FALSE, processInfoList[i].Process.dwProcessId);
                if (hProc != NULL) {
                    TerminateProcess(hProc, 1);
                    CloseHandle(hProc);
                }
            }
        }
    }

    RmEndSession(dwSessionHandle);
    return 1;
}
```

By terminating only the specific processes holding open handles rather than crashing system-wide services indiscriminately, Conti ensures the host remains operational while rendering databases and document stores accessible for encryption.

### 2. Multithreaded Concurrency via I/O Completion Ports (IOCP)

Sequential directory traversal and file encryption introduce severe I/O bottlenecks. Conti v3 addresses this by decoupling filesystem traversal from encryption using Windows **I/O Completion Ports (IOCP)**:

* **Dynamic Worker Thread Scaling:** Rather than hardcoding a static thread count across all machines, Conti v3 inspects the host's hardware profile via `GetSystemInfo` to determine `dwNumberOfProcessors`. It creates worker threads dynamically proportional to logical CPU cores (often double the number of logical cores), maximizing multi-core throughput without causing scheduler starvation.
* **Work Queue Distribution:** A master thread walks filesystem directories and network shares, packaging each qualifying file path into an IOCP work item dispatched via `PostQueuedCompletionStatus`.
* **Asynchronous Execution:** Dedicated worker threads waiting on `GetQueuedCompletionStatus` dequeue tasks, execute the Restart Manager check, perform file encryption, and append the metadata footer concurrently.

```text
┌─────────────────────────────────────────────────────────────┐
│ MASTER DIRECTORY TRAVERSAL THREAD                           │
│ - Enumerates volumes, local drives, and network shares      │
│ - Filters file extensions against exclusion lists           │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼ (PostQueuedCompletionStatus)
┌─────────────────────────────────────────────────────────────┐
│ WINDOWS I/O COMPLETION PORT (IOCP) WORK QUEUE               │
└──────┬───────────────────────┼───────────────────────┬──────┘
       │                       │                       │
       ▼                       ▼                       ▼
┌──────────────┐        ┌──────────────┐        ┌──────────────┐
│ WORKER T-01  │        │ WORKER T-02  │        │ WORKER T-NN  │
│ - RmGetList  │        │ - RmGetList  │        │ - RmGetList  │
```

### 3. Cryptographic Pipeline: ChaCha20 / RSA-4096 Hybrid Encryption

Conti v3 employs a hybrid encryption scheme designed to balance encryption speed with cryptographic security:

1. **Symmetric Encryption (ChaCha20):** For each target file, the worker thread generates a cryptographically random symmetric key (256-bit) and nonce (64-bit). The file contents are encrypted using the ChaCha20 stream cipher. In certain builds, Conti supports partial encryption modes (encrypting only the file header or blocks of large files) to drastically accelerate execution speed against large database stores.
2. **Asymmetric Key Protection (RSA):** The symmetric ChaCha20 key and nonce are encrypted using an embedded master public RSA key (typically RSA-4096 in standard v3 enterprise builds, or RSA-2048 in select test builds).
3. **Metadata Footer:** The encrypted symmetric key, nonce, and marker metadata are appended to the end of the encrypted file. The original file extension is replaced with the campaign extension (earlier builds used `.CONTI`; later campaigns used randomized or victim-specific extensions).
4. **Decryption Guarantee:** Because the attacker's master private RSA key is retained exclusively on the syndicate's backend servers, recovery of the per-file ChaCha20 keys without paying the extortion demand is mathematically infeasible.

### 4. Dynamic API Resolution via Compile-Time String Hashing

To hinder static analysis and prevent automated security software from flagging its Import Address Table (IAT), Conti v3 resolves critical Windows API functions dynamically at runtime:

* Rather than storing plaintext ASCII strings like `"VirtualAlloc"` or `"TerminateProcess"` in the binary, Conti stores precomputed hash values (using MurmurHash3 or custom polynomial string hashes).
* At initialization, the malware walks the Process Environment Block (PEB) to locate loaded modules (`kernel32.dll`, `ntdll.dll`, `rstrtmgr.dll`).
* It traverses each module's Export Address Table (EAT), calculates the hash of each exported function name, and compares it to the precomputed target hash, retrieving the function pointer directly.

## Defensive Engineering & DFIR Lessons

The Conti syndicate's operational sophistication underscores several core defense-in-depth imperatives:

### 1. Disrupt the Early Kill Chain
Ransomware encryption is the final stage of an intrusion, not the first. By the time the Conti v3 locker binary executes, threat actors have typically spent days or weeks enumerating Active Directory, escalating privileges, and exfiltrating terabytes of data. Organizations must focus telemetry on early loader execution (BazarLoader, QakBot) and anomalous lateral movement.

### 2. Behavioral Monitoring of Restart Manager APIs
Security products and EDR agents should monitor for unexpected user-mode processes loading `RstrtMgr.dll` and calling `RmStartSession` / `RmGetList`. Legitimate administrative software rarely enumerates and terminates open database handles en masse outside of scheduled maintenance windows.

### 3. Immutable and Isolated Backups
Because Conti actively terminates database processes and wipes Volume Shadow Copies (`vssadmin delete shadows`), organizations must maintain offline, immutable, or out-of-band backups that cannot be modified via compromised Domain Administrator credentials.
